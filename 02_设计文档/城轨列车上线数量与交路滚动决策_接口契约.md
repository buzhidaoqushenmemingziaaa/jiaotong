## 0.1  接口冻结原则
**第一周末（W1 末）必须完成接口冻结。**冻结之后，本文件第 3、4 两节的字段名与函数签名不再由个人单独修改**；确需变更时，提出来、改本文件、全队同步，再改代码。**
冻结的意义很直接：B 写引擎、C 写界面，两人并行开发。只要各自对着同一份契约写，W4 对接时接口一定对得上。**接口不冻结，就是两个人各写各的，联调时全部返工。**

## 0.2  三条不许破的约定
- **引擎不依赖界面**：`engine/` 目录下禁止出现 `import tkinter`。
- **界面不建模型**：`ui/` 只做“读配置 → 调 run_case → 画结果”三件事。
- **结果靠返回值传递**：引擎不靠 `print` 输出结果，一律通过返回的 dict 传出。

## 1.3  决策周期与时间索引
时段索引 t 从 **1** 开始（不是 0），因为 C6 的时滞式里要用到 t − τd。初始状态单独放在 `initial` 里，用索引 0 表示。

| **索引** | **含义** | **14 号线取值** |
| --- | --- | --- |
| t ∈ T | 决策时段 | 1 … 16（每步 15 min，共 4 h） |
| m ∈ M | 区段（区间） | 1 … 17（18 座车站切成 17 段） |
| d ∈ D | 车场 | D1 昂鹅车辆段、D2 福新停车场 |
| r ∈ R | 交路 | r0 全线、r1 南约折返、r2 四联折返 |
| k ∈ K | 车底档位 | 0, 2, 4, …, 44（共 23 档） |
| s ∈ S | 车站 | 1 … 18 |

## 1.4  服务层：B 与 C 的界面契约
**B 写引擎、C 写界面，两人**并行开发**。分界线只有一条：**服务层的三个函数**。**

|  | **B（引擎开发）** | **C（系统与产品）** |
| --- | --- | --- |
| 拥有 | `engine/` 全部文件 + `run_case.py` | `ui/` 全部文件 |
| 产出 | 求解结果、图、校验报告 | 可操作的界面、用户导出的文件 |
| 不许碰 | **`ui/` 里的任何文件** | **`engine/` 里的任何文件** |
| 访问对方的唯一方式 | —（不访问） | `import run_case`，用下面三个函数 |

服务层对外只有三个函数**（都在 `run_case.py` 里）：**

```python
def describe_config() -> dict:
    """UI 表单描述：字段名、类型、单位、必填、可编辑性、取值范围、中文说明、分组。"""

def describe_errors() -> dict[str, str]:
    """错误码 → 中文提示。C 只负责渲染，不负责编写文案。"""

def run_case(config, peak=None, progress_cb=None, time_limit_s=180,
             mode="single", forecast=None, window=None) -> dict:
    """唯一求解入口。config 为文件路径或已解析的 dict。

    mode     : "single"   单期全时域优化（默认，旧行为）
               "rolling"  滚动时域闭环：每步重优化、只执行第一步
    forecast : 预测序列（见 §1.6）。None 表示用真值（完美预测，作理想基准）
    window   : 滚动时的优化时域长度（步）。None = 不截断（推荐）
    """
```

**`describe_config()` 的返回结构：**

```
{
  "groups": [
    {
      "id": "line",
      "title": "接口一：线路参数",
      "fields": [
        {"key": "line.stations",   "label": "车站列表",
         "type": "list[str]", "unit": "", "required": True,
         "editable": True,  "doc": "按运行方向排列，长度 N"},
        {"key": "line.total_length_km", "label": "线路全长",

```

为什么要这个函数**：界面要给几十个字段生成输入框。如果 C 手抄一份字段表，B 改一个字段名，界面就静默失效——而且这种 bug 很难发现。由引擎描述自己的 schema，字段表只有一份，永远不会漂。**
`editable: False` 的字段在界面上渲染为只读（灰色），例如由其他参数派生的线路全长、拥挤分段点 ρ2。这些值由引擎算，界面不许让用户手改。

## 1.5  六个容易撞车的点

| **易撞车的地方** | **谁做主** | **怎么处理** |
| --- | --- | --- |
| 界面怎么知道有哪些字段 | B | C 调 `describe_config()` 动态生成表单，**禁止手抄字段表** |
| 图表归谁 | B（`engine/viz.py`） | C 调 `viz.plot_*()` 拿到 PNG 路径再显示。**这样界面图与论文图同源**，不会出现「论文里的图和界面上的图对不上」 |
| 错误提示文案 | B | B 在 `describe_errors()` 里给全部错误码配中文；C 只做 `code → 文案` 的查表渲染 |
| 求解时界面卡死 | C | C 在 worker 线程里调 `run_case`；B 提供可选的 `progress_cb` 回调，不传也能跑 |
| 改完参数保存时冲掉注释 | C | 配置里大量 `_xxx` 开头的键是给人看的说明（`_placeholders`、`_note`）。C 保存时必须**原样保留所有 `_` 开头的键**，只改用户编辑的字段 |
| 界面自己做校验 | B | C 不许实现任何校验逻辑。校验是引擎的 `validate.py`，界面只负责**显示**它返回的报告 |

**★ **Tkinter 不是线程安全的**——这条最容易踩。**

```python
# ✗ 错的：worker 线程里直接改控件
def worker():
    res = run_case(cfg)
    label.config(text=res['summary']['objective'])    # 崩溃或静默失效

# ✓ 对的：结果放队列，主线程轮询
def worker():
    q.put(run_case(cfg))

def poll():
    try:
        res = q.get_nowait()
        render(res)                                    # 主线程里改控件
    except queue.Empty:
        root.after(100, poll)
```

★ **图片引用要留着**——Tkinter 的 `PhotoImage` 被垃圾回收后，界面会变成一片空白。

```
img = tk.PhotoImage(file=png_path)
label.image = img        # 必须挂住引用，否则显示空白
label.config(image=img)
```

Tk 8.6 **原生支持 PNG**，不需要 Pillow；`engine/viz.py` 直接输出 PNG 即可。若要做可缩放的交互图，可改用 `FigureCanvasTkAgg`（本机 matplotlib 后端已是 tkagg，两条路都验证过可用）。

## 1.6  B 与 D 的第二个接口：预测序列（v1.2 新增）
**课题标题里的「预测不确定性」由**预测序列**引入。这一层的数据由 D 负责，引擎由 B 负责，两者的分界是一条数据契约。**

| **项** | **D（数据与实验）** | **B（引擎开发）** |
| --- | --- | --- |
| 拥有 | 预测生成模块（误差注入、误差标定） | 求解与滚动闭环 |
| 产出 | 预测序列 q̂(t,m) 与组候车需求 q̂grp(t,g) | 实际成本、后悔值、逐列车方案 |
| 不许做 | **不许碰 `engine/`** | **不许自己生成需求或误差** |
| 交付形式 | 二维数组（或 JSON/CSV），形状 [T][M] / [T][G] | 只按数组消费，不关心误差怎么来的 |

数据契约**（B 只认这个结构，不认误差模型）：**

```
forecast = {
  "mode": "rolling",          # 或 "single"
  "mape": 0.20,                # 仅用于报告，引擎不使用
  "seed": 0,
  "q":    [[...], ...],          # [T][M] 断面客流（人/h）
  "qg":   [[...], ...],          # [T][G] 各 OD 服务组候车人数（人/h）
  "at":   {0: {...}, 4: {...}},  # 可选：站在第 t 步的预测（滚动用）
}
```

**★ **约定**：`q` 与 `qg` 里放的一律是**预测值**，绝不放真值；真值由 config 的需求块给出。引擎内部负责把两者对比、算出后悔值。这样 D 换任何误差模型，B 的代码都不用改。**
**★ **滚动时的自洽性要求**：`at[t0]` 必须是「站在第 t0 步看未来」的预测，且与 `at[t0−1]` 使用**同一批随机数**（只把提前期重新起算）。**禁止每步重新抽随机数**——那样闭环会凭空获得信息，结论失真。这条由 D 保证，B 只负责按 `at[t0]` 求解。**

| --- | --- | --- |

★ 这里有两个必须分清的坑**：`min_time_s` 与顶层 `turnback_cycle_min` 是两个不同的量；`capacity_tph` 是实际能力而非理论上限。**

### （K1）折返的四个量：最小折返时间、缓冲、周期、实际能力
tturncycle  =  tturnmin  +  trec
Tr  =  2 · Rr  +  2 · tturncycle
Capturn上限  =  ntk · 3600 / tturnmin
须满足   Capturn实测  ≥  Fmcap          ∀ m ∈ 折返站所在区段
**式中：**
tturnmin  ——  最小折返时间，列车物理占用折返线。14 号线四站均取 180 s（2–3 min 上界）
trec  ——  折返缓冲与恢复时间，含进路办理与司机换端确认。14 号线取 120 s
tturncycle  ——  单端折返周期 = 180 + 120 = 300 s = 5.0 min，进 Tr
Capturn上限  ——  折返能力的理论上限，只计折返线占用时间
Capturn实测  ——  配置里 capacity_tph 填的是这个值
Tr  ——  交路 r 的往返周期（min）
ntk  ——  折返线股道数
Fmcap  ——  折返站所在区段的通过能力上限（列/h）
**作用：四个量各管一段，混用会同时算错周期与能力。**只代入物理折返时间 3 min 得 Tr0 = 106 + 6 = 112 min，与首班车时刻反推的 116 min 对不上**；补上 2 min 缓冲后三个交路全部吻合（116 / 76 / 50）。《模型规范》§2.1 已相应补充 trec 行。**
**上限不能当实际能力用**：上限未计进路办理、司机换端确认与站台作业时间，实际必低于上限。14 号线四站均为站后折返、tturnmin = 180 s，岗厦北/沙田 2 条折返线，上限 40 列/h 取 25（62%）；四联/南约 1 条，上限 20 列/h 取 12（60%）。若把 40 当实际能力，方案排到现实中会排不开。
trec 是由 Tr 反算的平衡项，不是独立实测值。拿到运行图上的实际折返作业时分后应以实测值替换。
自检：① `check_config.py` 已内置交路周期与折返能力两项检查；② 若实测能力达到上限的 90% 以上，应复核进路作业时间是否被低估。

CSV 数据的格式约定**（D 按此产出，B 按此读取）：**

```
# 文件名由 demand.path 指定，UTF-8 编码，逗号分隔
t, sec1, sec2, sec3, ..., secM
1, 42000, 38500, 33000, ..., 9500
2, 44500, 40800, 35000, ..., 10100
...
16, 12000, 11000,  9800, ...,  3200

# 行数 = horizon_steps（不含表头）
# 列数 = N − 1（区段数）
# 单位统一为 人/h
```

### （D1）客流数据的四分量纲与误差约定
qt,m = qt,m · ( 1 + εt,m ),      εt,m ~ U(−η, +η)
**式中：**
qt,m  ——  时段 t、区段 m 的真实断面客流（人/h），**配置或 CSV 里存的是这个**
qt,m  ——  模型实际可见的预测客流（人/h）
εt,m  ——  预测相对误差，**由引擎抽取**
η  ——  预测误差强度（MAPE），来自 scenario.forecast_error_mape
**作用：**配置与 CSV 里存的永远是真实客流 q，不是加过误差的 q̂。** 误差由引擎内部添加，因为同一个 q 要在不同 η 下反复跑——若 D 预先加了误差，η 扫描就没法做了。**
B 必须实现的读取校验（任一不过即报 E1002）：
① 行数 == horizon_steps；② 列数 == N − 1；③ 全部取值 ≥ 0；
④ 单位是 人/h——若 D 给的是「人/决策步」，必须乘以 4（Δ = 15 min）换算后再报错或自动换算，并在 messages 里留痕。
两峰分别给：`section_flow_peak_pax_per_h.morning` 与 `.evening`。两峰独立建模，各跑一次。
**B 不许在引擎里假设峰的名字。** 峰列表从 `scenario.peaks` 读，写成 `for peak in cfg.scenario.peaks`。
*对应公式依据：*[16] [15]

## 5.2  topology.py

### （T1）拓扑派生的三件事
Ar,m  =  1    若  origin(r) ≤ m < terminus(r)    否则  0
nm共  =  Σr ∈ R  Ar,m
Fmcap  =  3600 / hmin    其中 hmin = shared 若 nm共 ≥ 2，否则 exclusive
**式中：**
Ar,m  ——  交路—区段关联矩阵元素
origin(r)、terminus(r)  ——  交路 r 的起讫站索引
nm共  ——  区段 m 上叠加的交路数量
Fmcap  ——  区段 m 的通过能力上限（列/h）
hmin  ——  最小追踪间隔（s），共线段取 shared，否则取 exclusive

# 6  参数校验（求解前必做）
**对应《参数清单（通用版）》§6 的**八项**校验公式。**校验不过直接抛异常，不进求解器。**这能省掉大量“模型无解，查半天发现是参数填错”的时间。**
其中 V6 / V7 / V8 是 v1.1 新增：V6 对应规范 C14（在线总数上限），V7 对应 C15（折返能力上限），V8 针对初始待班口径。**V8 尤其重要——b₀ 取错会让核心创新① 在模型里失效。**

### （V1）交路覆盖
Σr ∈ R  Ar,m  ≥  1            ∀ m ∈ M
**式中：**
Ar,m  ——  交路—区段关联矩阵元素
M  ——  全线区段集合
**作用：每个区段至少被一个交路覆盖。为 0 说明该区段无车可跑，方案存在结构性缺口。**
*对应公式依据：*[8] [7]

### （V2）折返可行性
origin(r) ∈ Sturn    且    terminus(r) ∈ Sturn            ∀ r ∈ R
**式中：**
origin(r)、terminus(r)  ——  交路 r 两个端点的车站索引
Sturn  ——  折返站集合，由 turnbacks 派生
**作用：交路端点必须落在折返站集合内，否则该交路在物理上无法折返。**
*对应公式依据：*[18] [8]

### （V3）车底数充足
Σd ∈ D  nd  ≥  apeak  +  areserve
apeak  =  Σr ∈ R  frpeak · Tr / 60
**式中：**
nd  ——  车场 d 的配属车底数
apeak  ——  高峰所需在线车底数
frpeak  ——  交路 r 的高峰目标发车密度（列/h）
areserve  ——  检修与备用车底数，取配属总数的 10%–15%
**作用：配属车底必须同时覆盖高峰在线需求与检修备用需求。**
*对应公式依据：*[17] [21]

### （V4）区段能力自洽
Σr ∈ R  Ar,m · 60 · arplateau / Tr  ≤  Fmcap            ∀ m
**式中：**
arplateau  ——  交路 r 高峰平台期的在线车底数
Fmcap  ——  区段 m 的通过能力上限（列/h）
**作用：目标高峰开行方案不得超各区段通过能力。**该式在共线段最易触发**。**
*对应公式依据：*[8] [2] [19]

### （V5）时段范围自洽
\|T\|  ≥  τ步  +  1
**式中：**
\|T\|  ——  决策时段总数
τ步  ——  离散化后的出库提前期（决策步数）
**作用：时段数必须大于时滞步数加 1。**否则模型无法做出任何有效决策**——第一列车上线所需的唤醒动作发生在时段开始之前，模型没有对应的决策变量。**
*对应公式依据：*[9] [17]

### （V6）在线车底总数上限（v1.1 新增，对应 C14）
Σr ∈ R  arplateau  ≤  navail
**式中：**
arplateau  ——  交路 r 高峰平台期的在线车底数
navail  ——  可用车底总数 = 配属 − 检修备用
**作用：**任一时刻的在线车底数不得超过可用车底总数。** 缺这一条时 C5/C6 只能推出 at ≤ a0 + Σu，初始在线车底未被扣除，模型在峰值可以声称用了超过配属的车底。**
*对应公式依据：*[17] [21]

### （V7）折返能力自洽（v1.1 新增，对应 C15）
60 · arplateau / Tr  ≤  Capturn(r)            ∀ r ∈ R
**式中：**
arplateau  ——  交路 r 高峰平台期的在线车底数
Tr  ——  交路 r 的往返周期（min）
Capturn(r)  ——  折返端车站的实测折返能力（列/h）
**作用：折返站作业能力限制了交路能开的列车数。由该式可反算各交路的车底数上限 ar ≤ Capturn(r)·Tr/60，这同时也**大幅压缩了 λ 的规模**（见《模型规范》§8 的分交路档位上界）。**
*对应公式依据：*[18] [8]

### （V8）初始待班口径（v1.1 新增）
b0,dinit  ≈  在段可用车底数            （不是「近满库」）
**式中：**
b0,dinit  ——  各车场的初始待班列车数，定义为「**已唤醒**、可立即上线」
在段可用车底数  ——  运营开始时已完成唤醒与整备的列车数，14 号线早高峰约 5 组
**作用：★ **这条决定核心创新① 是否成立。** 若 b0,dinit 取成「近满库」（如 40 列），模型开局就有 40 列车可用，C6 的时滞约束在整个高峰内都不会咬人——**出库提前期完全不产生代价，核心创新① 在模型里被架空。
正确口径与《建模蓝图》§0.4 的运营核算一致：早高峰在段可用仅约 5 组。
与 V3 联动：已唤醒的 b0,d 已占用配属，须从唤醒配额 Σx ≤ nd 中扣除。
*对应公式依据：*[17] [16]
