# 列车开行方案决策系统 —— 系统化设计稿

结论：能做，而且这个项目比一般课题更适合。

原因不是"运气好"，而是你已有的《接口契约》把 engine 设计成了不依赖界面的形态——

服务层 run_case.py 的三个函数天然就是 HTTP handler 的形状。

从 Tkinter 换到 Web 前后端，engine/ 一行都不用改。

## 1 为什么这个项目天生适合系统化

| 已有资产 | 在系统里扮演什么 | 还缺什么 |
| --- | --- | --- |
| engine/（B 的代码） | 计算内核，原样复用 | 无 |
| run_case.py 三个函数 | API handler 的核心逻辑 | 外面包一层 HTTP |
| line14.json 配置 schema | API 请求体 + 前端表单的自动生成源 | 无 |
| results dict（a/x/u/b/F/g1/g2/params_used） | API 响应体 | 分页与摘要 |
| acceptance_check.py | 自动化测试套件（现成） | 无 |
| viz_rail.py 出图脚本 | 可视化模块（后端已有的图） | 前端交互化 |
| check_config.py / check_genericity.py | 输入校验服务 | 无 |

关键：《接口契约》§1.2 的三层调用链

ui/app.py  →  run_case(config, peak)  →  engine.*

把第一层换掉，第二三层不动，就是 Web 后端。

## 2 系统是什么产品

定位：城市轨道交通列车开行方案辅助决策系统

用户：线路规划人员、行车调度员、教学科研

核心价值：不懂 MILP 的人也能——

录入/导入一条线路

一键生成最优开行方案（各时段各交路开多少车）

看到列车在线路上怎么跑、客流怎么变

对比不同方案、做敏感性分析

一键导出决策报告

### 八大功能模块

| # | 模块 | 说明 |
| --- | --- | --- |
| 1 | 线路建模 | 表单录入或从 Excel 导入线路拓扑（站序、里程、区间时分、折返站、车辆段） |
| 2 | 参数配置 | 表单由 describe_config() 自动生成，禁止手抄（契约 §1.5） |
| 3 | 方案求解 | 异步任务 + 进度条 + 求解日志 |
| 4 | 运行可视化 | 列车运行动画、时空图、满载率热力、断面客流 vs 运力 |
| 5 | 方案对比 | 多方案（三级嵌套 / 两级 / 仅全线）并列对比 |
| 6 | 敏感性分析 | τ、配属数、需求倍数、cbd_scale、权重 扫描 + 曲线 |
| 7 | 报告导出 | 一键生成 docx/pdf 决策报告 |
| 8 | 诊断与帮助 | 瓶颈定位（如"共线段通过能力是瓶颈"）、约束违反提示、参数含义与公式 |

## 3 技术架构

```
┌─────────────────────────────────────────────────────────┐
│  前端  Vue3 + Vite + Element Plus + ECharts              │
│  ─ 参数配置（schema 驱动，自动渲染表单）                   │
│  ─ 求解页（任务提交 + 进度 + 日志）                        │
│  ─ 可视化页（列车动画 / 时空图 / 热力图）                  │
│  ─ 对比页、敏感性页、报告页                                │
└──────────────────────┬──────────────────────────────────┘
                       │ REST / JSON（+ 轮询或 SSE 推送进度）
┌──────────────────────▼──────────────────────────────────┐
│  后端  FastAPI（Python，与 engine 同语言，零阻抗）          │
│                                                          │
│  /api/meta/schema        → describe_config()             │
│  /api/meta/errors        → describe_errors()             │
│  /api/config/validate    → check_config.py 的逻辑         │
│  /api/line/import        → Excel/CSV → config            │
│  /api/solve              → 建任务（异步，返回 task_id）    │
│  /api/task/{id}          → 进度 / 结果摘要                │
│  /api/task/{id}/series   → 时序明细（分页）               │
│  /api/compare            → 多方案对比                     │
│  /api/sweep              → 敏感性扫描（异步）             │
│  /api/export/{id}.docx   → 报告导出                       │
│  /api/anim/{id}.gif      → 动画导出                       │
│                                                          │
│  ├── run_case.py   ★ 原样复用，只被 handler 调用           │
│  └── engine/       ★ 原样复用，一行不改                    │
└─────────────────────────────────────────────────────────┘
```

为什么后端用 FastAPI 而不是 Java/Go：

engine 是 Python + PuLP。换语言就要跨进程或重写模型，这是最大的浪费。

FastAPI 与 engine 同进程，直接函数调用，零阻抗。

## 4 ★ 关键决策：Tkinter 桌面版怎么办

不要推翻，要做成两条产品线。

|  | 单机版（Tkinter） | 在线版（Web） |
| --- | --- | --- |
| 定位 | 离线可用、现场演示不怕断网 | 展示效果、多人访问、易截图 |
| 用户 | 单个调度员 | 教学、评审、团队协作 |
| 部署 | 双击即用，零安装 | 服务器 / 本机 uvicorn |
| 复用 | engine/ + run_case.py | engine/ + run_case.py |

这两个前端共用同一个 engine，不是重复劳动。

《接口契约》的"铁律"（engine 不许 import tkinter）正是为此准备的——

它保证了引擎与界面解耦，所以可以挂任意多个前端。

答辩时这反而是个亮点："同一套引擎，两种交付形态" 说明架构是干净的。

⚠️ 但《接口契约》§1.5 里 Tkinter 特有的那两条要改：

"Tkinter 不是线程安全 → worker 线程 + queue.Queue + root.after"

"PhotoImage 引用要留着"

Web 版没有这两个问题（HTTP 请求天然并发，图片走 URL）。

建议把 §1.5 拆成"通用六点"+"桌面端专有两点"+"Web 端专有两点"。

## 5 后端接口清单

### 5.1 元数据（前端表单的自动生成源）

```
GET /api/meta/schema
→ describe_config() 的返回结构
   { "fields": [ {key, label, type, unit, required, default, enum?, range?, desc} ], ... }
```

前端不写死任何字段——契约 §1.5 已明确规定"禁止手抄字段表"。

这条规则换成 Web 一样成立，而且是前端能快速迭代的关键。

```
GET /api/meta/errors
→ describe_errors()：错误码 → 中文文案
```

### 5.2 求解（异步）

```
POST /api/solve
body: { "config": {...}, "peak": "morning", "time_limit_s": 180 }
→ { "task_id": "abc123" }

GET /api/task/abc123
→ { "status": "running|done|failed",
    "progress": 0.62, "stage": "构建模型",
    "summary": { "objective": 0.09373, "peak_online": 35,
                 "alloc": {"r0": 28, "r1": 5, "r2": 2},
                 "shared_flow": 20.83, "solve_time_s": 4.2 },
    "logs": [...] }
```

★ 必须异步。单次求解 3–7 s，但敏感性扫描要跑 36+ 次 = 几分钟。

同步阻塞 HTTP 会超时。

务实做法：BackgroundTasks + SQLite 任务表 + 前端轮询。

不要上 Celery + Redis——对本科项目是过度设计，多两个组件就多两倍的部署故障。

### 5.3 时序明细（分页）

```
GET /api/task/abc123/series?field=a&from=0&to=16
→ { "rid": ["r0","r1","r2"], "a": [[...]], "F": [[...]], ... }
```

results 里 a/x/u/b/s/F/g1/g2 各 16 步 × 若干维，一次全返回也就几百 KB，

但加上敏感性扫描的多方案就要分页。

### 5.4 对比与扫描

```
POST /api/compare
body: { "config": {...}, "variants": [["r0","r1","r2"], ["r0","r1"], ["r0"]] }
→ 各方案的目标值 / 等待 / 拥挤 / 车公里 / 峰值在线

POST /api/sweep
body: { "config": {...}, "param": "cbd_scale", "values": [0.06,0.09,0.12,...] }
→ 扫描结果 + 曲线数据
```

这两个是最能体现"系统 ≠ 求解器套壳"的功能——它们做的是决策支持，不是算一次给个数。

### 5.5 导出

```
GET /api/export/{id}.docx    决策报告（复用现有 python-docx 生成器）
GET /api/anim/{id}.gif       列车运行动画（复用 viz_rail.py）
```

## 6 前端页面设计

| 页面 | 组件 | 说明 |
| --- | --- | --- |
| 首页/线路管理 | 线路列表、新建/导入 | 支持多条线路（14 号线、测试线…） |
| 参数配置 | schema 驱动表单 | 由 /api/meta/schema 渲染，带单位、范围校验、默认值 |
| 求解 | 提交 + 进度条 + 日志 | 进度用 SSE 或轮询 |
| 可视化 | ECharts + 播放控制 | 见下 |
| 对比 | 表格 + 雷达/柱状图 | 多方案并列 |
| 敏感性 | 折线图 + 数据表 | 拖动式扫描 |
| 报告 | 预览 + 下载 | 可勾选要包含的图表 |

### 可视化页（系统的门面）

列车运行动画 —— 线路示意图上列车方块移动

数据：/api/task/{id}/series 里的 a + 交路周期 → 前端算列车位置

ECharts custom 系列或 graphic 组件

播放/暂停/倍速/拖动时间轴

断面客流 vs 运力 —— 柱状 + 折线，与动画同步

满载率热力图 —— 里程 × 时间

时空图（运行图） —— 多条折线

车底运用 —— 在线/唤醒/回段堆叠图

建议：动画前端实时算（可交互、可改倍速），

同时后端保留 viz_rail.py 生成 GIF 的能力（用于导出报告和离线演示）。

## 7 工程难点与务实解法

| # | 难点 | 务实解法 | 别做什么 |
| --- | --- | --- | --- |
| 1 | 长任务阻塞 | BackgroundTasks + SQLite 任务表 + 轮询 | ❌ Celery+Redis（过度） |
| 2 | 并发求解 | CBC 是单线程，加 asyncio.Semaphore(2) 限制并行 | ❌ 无限制并发（CPU 打满） |
| 3 | 结果数据量 | 摘要 + 分页明细，大对象存文件/SQLite | ❌ 全量塞进一个响应 |
| 4 | 进度反馈 | run_case(progress_cb=...) 已有回调，写进任务表 | ❌ 前端假进度条 |
| 5 | 进程被 kill | 求解子进程化，超时能中断 | ❌ 直接在 web 进程里跑（崩了整个服务） |
| 6 | 前后端联调 | 接口契约冻结后再动手（你已经有契约了） | ❌ 边写边改字段 |
| 7 | 部署 | uvicorn + 前端 vite build 产物由 FastAPI 静态托管 | ❌ 微服务 / K8s |

第 7 条特别说：竞赛演示不需要前后端分开部署。

vite build 出的静态文件让 FastAPI 用 StaticFiles 托管，

一个进程、一条命令启动，最稳。

## 8 怎么让它不像"求解器套壳"

评委最容易问的一句是："这不就是把模型包了个界面吗？"

要提前准备答案——系统里必须有求解器没有的东西：

| 卖点 | 现状 | 说明 |
| --- | --- | --- |
| ① 通用性 | ✅ 已验证 | check_genericity.py 通过，14 号线 + 测试线都跑得动。任意线路，不写死 |
| ② 可视化 | ✅ 已有 | 列车在线上跑 + 客流同步，这是大多数同类工具没有的 |
| ③ 瓶颈自动诊断 | ✅ 已有逻辑 | "共线段通过能力是瓶颈"这种结论自动给，不是让用户自己看数 |
| ④ 敏感性分析自动化 | ✅ 已有 | 一键扫 9 个 cbd 值 × 4 个方案 |
| ⑤ 方案对比与一键报告 | 🟡 需做 | 把实验脚本变成产品功能 |
| ⑥ 输入校验与友好报错 | ✅ 已有 | check_config.py + describe_errors() |
| ⑦ Excel 导入 | 🔴 需做 | 降低使用门槛的关键 |
| ⑧ 出库窗口诊断 | 🟡 可做 | 见 §10，把创新①产品化 |

最强的三条是 ①③④：通用性 + 自动诊断 + 自动敏感性分析。

这三条决定了它是决策支持系统而不是计算器。

★ 软著要最早启动——周期 1–3 个月，等你系统做完再申请就赶不上比赛了。

可以先按现有 engine + run_case.py 提交登记，Web 前端后续补充登记。

软著是登记制（形式审查），专利是审查制（2–3 年）。

竞赛要"发明的东西"，先拿软著最划算；专利可以同时申请但别指望赶上。

## 10 系统化能反过来加强论文（这条最值钱）

把之前发现的"出库窗口"问题产品化：

现有模型里 τ 是外生常数（郑州 7 / 武汉 13 / 西安 27 min）。

但实测发现高峰期就算提前 25 min 也插不进正线。

系统里加一个"出库可行性诊断"模块：

输入当前时段的共线段占用率

输出"本时段出库建议提前 X 分钟""本时段最多还能出库 Y 列"

可视化：正线追踪空隙的时间轴 + 出库列车能不能插进去

这直接把一个模型局限变成了一个产品功能，而且：

不需要新数据（只要 h_min 和 t^turn，你都有）

论文里可以作为"创新①的工程实现"

答辩时是个能用动画演示的亮点

这才是"系统化"最大的价值——不是为了比赛硬凑一个界面，

而是把研究里那些"算得出来但说不清"的东西变成看得见的东西。

## 13 一句话总结

能做，而且改动比想象的小——engine 和 run_case.py 原样复用，

只需要给 run_case 套一层 FastAPI，再写一个 Vue 前端。

《接口契约》的三层架构就是为此准备的。

真正的价值不在于"有个界面"，而在于把模型里的瓶颈诊断、

敏感性分析、出库可行性这些"算得出来但说不清"的东西变成看得见的——

那才是"发明"。
